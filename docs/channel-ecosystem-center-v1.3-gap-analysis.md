# 知启云AI企业级渠道生态中心 V1.3 现有系统差异分析

> 分析日期：2026-07-26  
> 分析范围：`知启云AI企业级渠道生态中心V1.3正式版.docx`、当前仓库数据库迁移、Go 后端核心结算链路、Vue 管理后台现有模块。  
> 阶段约束：本阶段只分析和设计，不修改业务代码，不执行数据库迁移，不进入功能开发。

## 1. 结论

当前系统具备较高复用价值，用户、订单、支付、套餐、代理身份、运营中心、分润引擎、佣金记录、钱包、提现、企业租户和权限等基础能力已经存在，不应重建。

但是，当前数据库和代码结构只与 V1.3 部分匹配，尚不具备直接编码上线条件。主要原因不是缺少分润公式，而是以下业务和技术口径尚未统一：

1. V1.3 规定单笔订单只计算直属代理和所属运营中心，并禁止查询直属代理以上层级；此前需求包含上一级代理 50 元和最多两级代理分润，两者不能同时作为默认规则生效。
2. V1.3 将运营中心的 5000 元定义为技术服务费，并在一年内完成年度目标后发放 5000 元运营绩效奖励；此前需求将其定义为可退保证金，并以直属发展 30 个代理作为退款条件。两种模型的会计、退款和流水结构完全不同。
3. 当前系统同时存在固定身份套餐结算、旧营销分润规则和新版 CommissionEngine 三条规则路径，尚未收敛为单一商业规则源。
4. 当前规则按单条记录保存版本，缺少整套规则的原子发布版本。一次订单可能命中不同发布时间的规则项，不能充分保证“历史订单按历史整套规则、新订单按新整套规则”。
5. 当前数据库已提供佣金负向记录和钱包负向流水的结构基础，但退款事件尚未形成覆盖佣金、冻结、待结算、已结算和平台留存的统一冲正编排。
6. 当前没有面向业务人员的商业规则模拟器 API 和管理后台页面。

因此本报告结论为：基础结构可复用，业务语义和规则治理不完全匹配；应先确认第 2 节的四项冻结决策，再进入数据库迁移和业务代码修改。

## 2. 编码前必须冻结的业务决策

| 编号 | 决策项 | V1.3 正式版 | 此前需求 | 建议 |
|---|---|---|---|---|
| D-01 | 代理分润深度 | 仅直属代理，不计算更高代理层级 | 最多两级，部分会员订单给上一级代理 50 元 | 以 V1.3 为准时，默认收益深度固定为 1；若保留两级方案，应升级文档版本后再开发 |
| D-02 | 5000 元性质 | 运营中心技术服务费，达标后另发绩效奖励 | 可退保证金，发展 30 个直属代理后退款 | 建议二选一，不在同一字段中兼容两种会计含义 |
| D-03 | 推荐奖励 | V1.3 未定义 | 运营中心推荐运营中心 3000；代理推荐运营中心时代理 1000、运营中心 2000 | 明确纳入 V1.3 后续小版本，或明确本期排除 |
| D-04 | 规则范围 | 金额、比例、套餐、奖励、周期、退款规则均可配置 | 另要求层级上限、退款冲减顺序、保证金返还后分润资格可配置 | 形成完整配置字典和默认值表后发布第一版规则集 |

在上述决策确认前，不应创建业务迁移或修改结算代码。

| 渠道关系管理 | 已有客户归属页面和渠道增长页面 | 部分匹配 | 可复用查询和展示，需增加关系历史、异常检测、调整审批和订单快照查看 |

| 领域 | 可复用内容 | 复用方式 |
|---|---|---|
| 用户与身份 | `xz_users`、用户角色、代理档案、运营中心档案 | 保留单一用户主体，通过代理/运营中心档案承载渠道身份 |
| 企业与权限 | `xz_tenants`、`xz_tenant_members`、企业角色、财务权限 | 所有新增规则、钱包、关系和结算接口继续强制 tenant scope 与 RBAC |

| 支付与履约 | 现有支付状态机、支付回调、微信虚拟支付、统一权益发放入口 | 支付成功只触发一次统一商业履约，不在渠道模块另建支付逻辑 |

| 佣金钱包 | `xz_commission_wallet_accounts`、`xz_commission_wallet_ledger` | 作为佣金资金权威账本，旧代理钱包和营销钱包降为兼容读模型 |
| 提现与付款 | 结算申请、申请明细、付款批次、付款明细、对账差异 | 复用现有审核与付款状态机，不新造提现体系 |

| 审计 | 财务审计日志、企业审计日志 | 所有规则发布、关系调整、模拟保存和人工冲正必须留痕 |

## 5. 当前结构需要扩展的部分

### 5.1 规则治理

现有 `xz_commission_rules` 已具备单条规则版本和生效时间，建议增量增加：

| 扩展项 | 目的 |
|---|---|
| `rule_set_id`、`rule_set_version` | 将套餐、Token、各受益方、平台剩余、退款政策作为一套规则原子发布 |
| `scenario_code` | 明确 MEMBER_BUY、AGENT_JOIN、OPERATION_CENTER_JOIN、OPERATION_PERFORMANCE 等场景 |
| `published_at`、`published_by` | 区分草稿、已发布、已停用和归档状态 |
| 发布校验 | 校验收益合计不能超过实付金额、平台剩余唯一、同一场景生效窗口不重叠 |
| 禁止原地改历史版本 | 管理端编辑已发布规则时必须复制为新版本 |

建议新增 `xz_commercial_rule_sets` 作为规则集头表，继续复用 `xz_commission_rules` 作为现金分润规则明细。套餐权益和运营绩效规则应通过同一规则集版本关联，不能仅靠名称约定。

### 5.2 历史订单快照

建议新增 `xz_order_commercial_snapshots`，一笔订单一条不可变快照，至少保存：

| 字段组 | 内容 |
|---|---|
| 规则身份 | `rule_set_id`、`rule_set_version`、发布时间 |
| 套餐快照 | 套餐价格、实付金额、Token 权益、有效期 |
| 关系快照 | 购买用户、直属代理、所属运营中心、关系来源和关系生效时间 |
| 计算输入 | 场景、币种、退款政策、冻结周期 |
| 计算输出 | 各受益方金额、平台剩余、舍入明细、校验结果 |
| 审计信息 | request id、幂等键、计算引擎版本 |

该快照是历史订单重放和退款冲正的依据，不能在退款时重新查询当前关系或当前规则。

### 5.3 渠道关系历史

继续用 `xz_agent_profiles` 保存当前有效关系，同时新增 `xz_channel_relation_history` 保存每次绑定、调整和失效：

| 核心字段 | 说明 |
|---|---|
| `subject_type`、`subject_id` | 代理或会员 |
| `direct_agent_id` | 当时的直属代理 |
| `operation_center_id` | 当时所属运营中心 |
| `effective_start_at`、`effective_end_at` | 关系有效区间 |
| `change_type`、`reason`、`approved_by` | 调整原因和审批审计 |
| `source_type`、`source_id` | 邀请码、后台绑定、迁移或其他来源 |

无限发展只影响组织关系存储，不代表收益计算必须递归。订单计算应直接读取下单时有效的直属代理和运营中心并写入快照。

### 5.4 运营中心政策

若采用 V1.3 的“技术服务费 + 绩效奖励”模型，建议新增：

| 表 | 作用 |
|---|---|
| `xz_operation_center_policies` | 配置技术服务费、考核周期、目标指标、目标值、奖励金额和生效版本 |
| `xz_operation_center_goal_periods` | 保存每个运营中心每个年度周期的目标、完成值和状态 |
| `xz_operation_center_performance_rewards` | 保存达标确认、奖励金额、规则版本、发放状态和负向冲正 |

若最终采用“保证金 + 达标退款”模型，应改为保证金账户和保证金交易流水，不应复用绩效奖励表。该分叉必须在迁移设计前确认。

### 5.5 退款冲正

建议新增 `xz_commercial_refund_adjustments` 作为一次退款的编排头记录，继续使用现有佣金记录和钱包账本保存资金事实。处理顺序应由规则配置，但同一次退款必须在一个事务或可恢复状态机中完成：

1. 读取原订单商业快照。
2. 按原规则版本计算本次退款比例和冲正金额。
3. 生成佣金 `REVERSAL` 或 `ADJUSTMENT` 负向记录。
4. 冲减预期、冻结、可提现、结算中或已结算余额，余额不足时进入 recoverable。
5. 生成平台留存负向流水和 Token 权益回收/欠额记录。
6. 若佣金已进入付款批次，阻断、拆分或生成追偿任务。
7. 记录完整幂等键、前后余额和审计日志。

## 6. 不应重复新增的结构

| 禁止新增 | 原因 | 应复用结构 |
|---|---|---|
| 新用户表或渠道用户表 | 会造成登录主体和身份重复 | `xz_users` + 代理/运营中心档案 |
| 新订单表或渠道订单表 | 会破坏支付、退款和履约一致性 | `xz_orders` + 商业快照 |
| 新支付回调 | 会形成重复履约和重复扣费风险 | 现有支付状态机和统一履约入口 |
| 新佣金钱包 | 当前已经存在多套钱包投影 | `xz_commission_wallet_accounts` + ledger |
| 新提现系统 | 现有结算申请和付款批次已覆盖 | 现有 settlement/payout 结构 |
| 第四套分润规则表 | 当前已有旧营销规则和新版规则 | 收敛到 `xz_commission_rules` + 规则集头表 |

## 7. API 差异与建议

### 7.1 现有可复用 API

| API | 用途 | 处理建议 |
|---|---|---|
| `GET /api/v1/admin/commission-rules` | 查询分润规则 | 保留，升级为按规则集和版本查询 |
| `POST /api/v1/admin/commission-rules` | 新增规则 | 保留为草稿规则项创建，不允许直接激活孤立规则 |
| `PUT /api/v1/admin/commission-rules/:id` | 更新规则 | 已发布版本禁止原地更新，改为复制新版本 |
| `GET/PATCH /api/v1/admin/marketing/commission-rules` | 旧营销规则 | 进入兼容只读/迁移状态，停止作为新订单权威来源 |
| 企业、客户归属、订单、支付、钱包、结算 API | 基础业务能力 | 继续复用并补充渠道权限和快照查询 |

### 7.2 建议新增 API

| API | 用途 |
|---|---|
| `GET /api/v1/admin/channel-rule-sets` | 查询规则集和版本 |
| `POST /api/v1/admin/channel-rule-sets` | 创建规则集草稿 |

| `POST /api/v1/admin/channel-rule-sets/:id/validate` | 发布前完整性和金额守恒校验 |
| `POST /api/v1/admin/channel-rule-sets/:id/publish` | 原子发布规则集 |
| `GET /api/v1/admin/channel-rule-sets/:id/diff` | 比较两个版本差异 |

| `POST /api/v1/admin/channel-rule-simulator/replay-order` | 使用历史订单快照重放原规则 |

模拟器请求不得创建真实订单、支付单、佣金记录或钱包流水。响应必须返回规则版本、关系解析结果、权益结果、各受益方金额、平台剩余、金额守恒校验和解释明细。

## 8. 管理后台页面差异与建议

当前后台已有客户归属、渠道增长和企业管理页面，可以复用布局、筛选、权限和 API Client。V1.3 仍需增加以下业务页面：

| 页面 | 核心能力 |
|---|---|
| 渠道生态中心 | 运营中心、代理、会员、订单、分润、异常和待办总览 |
| 商业规则中心 | 规则集草稿、版本、差异、校验、发布、停用和审计 |
| 套餐中心 | 套餐价格、Token 权益、有效期和关联规则集版本 |
| 渠道关系管理 | 无限关系树、直属关系、运营中心归属、历史和异常修复 |
| 分润中心 | 按订单展示规则快照、收益明细、冻结、可结算和冲正 |
| 钱包与提现 | Token、佣金、冻结、可提现、已提现、追偿和完整流水 |
| 运营中心管理 | 技术服务费、年度目标、完成进度、绩效奖励或保证金状态 |
| 商业规则模拟器 | 选择场景/版本/模拟关系，无支付演算结果并支持版本对比 |
| 数据看板 | GMV、Token 权益成本、代理收益、运营中心收益、平台留存、退款冲减 |

页面请求必须统一走现有 Axios API Client；权限至少拆分为查看、编辑草稿、发布规则、关系调整、退款冲正、绩效确认和提现审核。

## 9. 推荐实施计划与阶段门禁

### 阶段 0：业务规则冻结

可复用：V1.3 场景和现有默认套餐数值。  
需扩展：形成完整配置字典、状态机和退款顺序。  
需新增：D-01 至 D-04 决策记录、六类或精简场景的最终验算表。

验收项：

- 明确收益深度是 1 级还是最多 2 级。
- 明确 5000 元是技术服务费/绩效奖励还是保证金/退款。
- 明确推荐奖励是否纳入本期。
- 每个场景满足金额守恒，平台剩余不得由前端传入。
- 业务方书面确认后才进入阶段 1。

### 阶段 1：数据库和规则治理

可复用：`xz_commission_rules`、佣金记录、佣金钱包、结算中心。  
需扩展：规则集外键、发布状态、历史不可变约束、现有规则迁移。  
需新增：规则集头表、订单商业快照、关系历史、退款编排头表；运营中心政策表按 D-02 选择。

验收项：

- 迁移只增量扩展，不删除现有数据。
- 已发布规则不能原地修改。
- 同一场景同一时间只能有一套有效规则集。
- 历史订单能定位唯一规则集版本和关系快照。
- 新旧钱包和规则表有明确权威源与兼容策略。

### 阶段 2：规则服务与模拟器

可复用：CommissionEngine。  
需扩展：规则集加载、场景解析、整套校验和解释输出。  
需新增：发布、版本差异、模拟、历史重放 API。

验收项：

- V1.3 会员场景模拟结果为 99600、40000、30000、20000、9600 分。
- V1.3 代理场景模拟结果为 99600、20000、30000、20000、29600 分。
- 模拟不创建订单、支付、佣金或钱包流水。
- 旧版本模拟结果在新版本发布后保持不变。
- 非法规则无法发布，所有失败有中文可解释原因。

### 阶段 3：订单支付与权益履约收敛

可复用：现有订单、支付回调、微信虚拟支付和权益发放入口。  
需扩展：履约时选定规则集、写商业快照、调用统一分润服务。  
需新增：旧固定结算和旧营销规则的兼容迁移开关。

验收项：

- 同一支付事件重复回调只履约一次。
- 套餐金额和 Token 权益只由服务端已发布规则决定。
- 订单、Token 权益、佣金、平台留存在同一事务或可恢复状态机中一致落账。
- 新订单只走统一规则源，旧订单仍可按旧快照查询和退款。

### 阶段 4：退款、钱包、提现和运营中心政策

可复用：负向佣金记录、佣金钱包账本、结算申请和付款批次。  
需扩展：退款冲正状态机、余额不足追偿、付款批次冲突处理。  
需新增：运营中心目标和奖励，或保证金账户和退款流程，取决于 D-02。

验收项：

- 未提现、待提现、结算中、已结算四种状态均有退款用例。
- 每次退款生成可追溯负向佣金和钱包流水。
- 部分退款按原规则版本计算，累计冲正不超过原收益。
- 运营中心奖励/退款只能发放一次并支持负向纠错。

### 阶段 5：管理后台和数据看板

可复用：Vue 3、Pinia、Axios、Element Plus、现有管理后台权限与页面壳。  
需扩展：客户归属、渠道增长、订单和财务页面。  
需新增：规则中心、模拟器、关系历史、运营中心政策和渠道看板页面。

验收项：

- 页面无硬编码商业金额和层级。
- 规则发布前必须经过校验和模拟。
- 高风险操作具备二次确认、权限和审计。
- 桌面端和常用管理分辨率可用，列表、金额和版本信息一致。

每个阶段完成后单独提交验收结果，未经确认不得自动进入下一阶段。

## 10. 风险评估

| 风险 | 等级 | 影响 | 控制措施 |
|---|---|---|---|
| V1.3 与此前两级分润规则冲突 | P0 | 分润对象和金额全部变化 | 阶段 0 书面冻结 D-01 |
| 5000 元会计性质冲突 | P0 | 影响退款、收入确认和运营中心资格 | 阶段 0 书面冻结 D-02，禁止同字段兼容 |
| 三套规则入口并存 | P0 | 同类订单可能产生不同结果 | 新订单收敛到规则集，旧入口只读兼容并设置退役计划 |
| 已发布规则可变 | P0 | 历史订单无法重放，审计失真 | 规则集原子发布、已发布版本不可变、订单保存完整快照 |
| 钱包体系重复 | P0 | 余额不一致和超额提现 | 明确佣金权威账本，其他钱包只做投影和对账 |
| 退款与提现并发 | P0 | 资金已支付后无法直接扣回 | 冻结期、状态锁、幂等键、recoverable 和追偿任务 |
| 渠道关系调整影响历史订单 | P1 | 退款或补算命中错误受益人 | 关系有效期和订单关系快照 |
| 套餐默认值仍硬编码 | P1 | 后台修改与实际履约不一致 | 数据库配置作为唯一权威源，代码仅保留安全启动策略 |
| 租户隔离遗漏 | P1 | 跨企业读取规则、钱包或关系 | 所有表和 API 强制 tenant_id、联合唯一键和越权测试 |
| 平台剩余出现负数 | P1 | 规则发布后订单亏损或无法入账 | 发布前金额守恒和边界校验，禁止依赖运行时兜底 |

## 11. 最终审批建议

当前不建议进入编码。建议先由业务负责人在 D-01 至 D-04 上给出确认，并以确认结果更新 V1.3 或发布 V1.3.1。确认后，先执行阶段 1 的数据库与规则治理设计评审，再修改任何订单履约或分润业务代码。

如果最终以 V1.3 正式版为唯一权威，则建议默认规则为：代理关系可无限发展，单笔收益深度为 1，仅直属代理和所属运营中心参与；5000 元按技术服务费处理，达标后另生成运营绩效奖励，不按保证金退款处理。该建议只有在业务方确认后才可转为实现要求。
