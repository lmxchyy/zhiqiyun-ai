# 知启云AI渠道生态中心 V1.3.1 现有系统差异分析

> 分析日期：2026-07-26  
> 业务依据：`知启云AI企业级渠道生态中心V1.3.1修正版.pdf`及本次任务说明。  
> 技术依据：当前仓库用户、订单支付、钱包、提现、权限后台、渠道关系和 CommissionEngine 结构。  
> 阶段约束：第一阶段只分析和设计，不修改业务代码，不执行数据库迁移，不进入功能开发。

## 1. 总体结论

当前系统具备建设 V1.3.1 的主要技术底座，用户、订单、支付、Token 权益、代理与运营中心身份、佣金计算、钱包、提现、财务权限和审计均有可复用模块，不应重复建设。

当前结构仍不能直接进入编码，原因如下：

1. 固定身份套餐结算、旧营销分润规则、新版 CommissionEngine 三条路径尚未收敛为单一商业规则源。
2. 套餐价格和 Token 权益仍存在 Go 代码默认常量，尚未满足全部商业金额后台配置的要求。
3. 现有规则按单条分润规则版本化，缺少整套商业规则的原子发布版本和订单完整快照。
4. 当前代理关系可以保存父代理和所属运营中心，但缺少完整关系历史、有效期和订单关系快照。
5. 现有模型没有独立的推荐奖励领域，不能准确表达“运营中心推荐运营中心”和“代理推荐运营中心”两类奖励。
6. 退款负向记录和钱包账本已有基础，但尚未形成覆盖佣金、推荐奖励、冻结、提现中、已结算和平台留存的统一冲正流程。
7. CommissionEngine 可以作为模拟计算内核，但目前缺少不产生真实订单和资金流水的模拟 API 与后台页面。

结论：V1.3.1 的底层能力可复用，规则治理、推荐奖励和历史快照需要增量扩展。确认本报告的规则边界后，才能进入数据库迁移设计和代码修改。

## 2. V1.3.1 商业规则基线

### 2.1 组织与收益边界

| 项目 | V1.3.1 基线 |
|---|---|
| 代理组织关系 | 支持无限发展和无限层级存储 |
| 单笔订单代理收益 | 只计算购买人或新代理的直属代理 |
| 运营中心收益 | 计算该直属代理所属运营中心 |
| 更高代理层级 | 禁止递归查询，禁止参与该订单收益 |
| 关系变更 | 不影响已经生成商业快照的历史订单和历史奖励 |

无限发展是组织关系能力，不等于无限分润。订单结算只需要读取直属代理和所属运营中心，不允许递归遍历祖先代理。

### 2.2 默认订单场景

所有金额为初始化配置，正式运行时必须从已发布规则版本读取。

| 场景 | 订单金额 | Token 权益 | 直属代理 | 运营中心 | 平台结算 |
|---|---:|---:|---:|---:|---:|
| 代理发展会员 | 996 元 | 400 元 | 300 元 | 200 元 | 96 元 |
| 代理发展代理 | 996 元 | 200 元 | 300 元 | 200 元 | 296 元 |

金额守恒公式：`实付金额 = Token 权益成本 + 直属代理收益 + 运营中心收益 + 平台结算`。

### 2.3 推荐奖励场景

推荐奖励不属于订单分润，不参与上述 996 元或 5000 元订单的平台剩余计算。建议作为独立营销费用事实建模，资金入账继续复用佣金钱包和提现体系。

| 推荐场景 | 默认奖励 | 受益人解析 |
|---|---:|---|
| 运营中心推荐运营中心 | 推荐运营中心 3000 元 | 推荐关系中记录的运营中心 |
| 代理推荐运营中心 | 推荐代理 1000 元 | 推荐关系中记录的代理 |
| 代理推荐运营中心 | 代理所属运营中心 2000 元 | 推荐事件发生时该代理所属运营中心的关系快照 |

推荐奖励必须满足：

- 与会员/代理订单佣金记录分开保存。
- 不查询推荐代理的上级代理，不向更高代理层级发放奖励。
- 同一被推荐运营中心、同一奖励项目只能触发一次。
- 奖励金额、触发事件、资格条件、冻结周期、撤销政策和预算来源全部后台配置。
- 推荐关系和受益人归属在触发时写入不可变快照，后续渠道关系调整不改变历史奖励。
- 被推荐运营中心订单退款、身份撤销或资格失效时，按原奖励规则版本生成负向奖励和钱包流水。

建议的默认触发事件为 `OPERATION_CENTER_ACTIVATED`：被推荐运营中心的开通订单已支付、统一履约成功且运营中心身份已激活后触发。触发时点仍需业务方最终确认。

### 2.4 运营中心政策

根据修正版可识别内容，运营中心默认支付 5000 元技术服务费，并在规定周期完成运营目标后获得默认 5000 元运营绩效奖励。技术服务费、目标周期、目标指标、目标值、绩效奖励和撤销政策均应后台配置并版本化。

运营绩效奖励与推荐奖励是两个独立业务场景：前者基于运营目标达成，后者基于有效推荐事件，不能共用同一业务记录类型。

## 3. 当前五大体系能力复用分析

### 3.1 用户体系

| 当前能力 | 复用判断 | 扩展要求 |
|---|---|---|
| `xz_users` 作为统一登录用户 | 直接复用 | 禁止新增渠道用户表 |
| 用户角色和企业租户成员 | 直接复用 | 新增渠道规则、奖励和钱包权限 |
| `xz_agent_profiles` 保存代理身份、父代理和所属运营中心 | 直接复用当前关系投影 | 增加关系历史、生效区间、防环校验和调整审计 |
| 运营中心档案 | 直接复用 | 增加推荐码、推荐来源、激活订单和政策版本关联 |
| 客户归属关系 | 扩展复用 | 订单和奖励必须保存当时的直属代理、运营中心快照 |

当前邻接关系可以表达无限代理树。收益计算服务不得沿 `parent_agent_id` 递归，只读取直接关系和所属运营中心。

### 3.2 订单支付体系

| 当前能力 | 复用判断 | 扩展要求 |
|---|---|---|
| `xz_orders`、订单状态和价格快照 | 直接复用 | 增加商业规则集和渠道关系快照 |
| 支付状态机、支付回调和幂等 | 直接复用 | 支付成功只调用一次统一商业履约 |
| 微信虚拟支付和权益发放 | 直接复用 | 金额、Token 权益只能来自服务端已发布规则 |
| 固定身份套餐履约 | 兼容迁移 | 收敛到统一规则集，停止继续扩展硬编码分支 |
| 旧营销分润 | 兼容只读 | 不再作为新订单或新推荐奖励的权威规则源 |
| CommissionEngine | 直接复用计算内核 | 增加规则集解析、结果解释和模拟模式 |

推荐奖励应由运营中心有效激活事件触发，而不是仅凭创建订单或收到支付回调触发。重复支付通知、重复履约和重复激活事件必须共享同一幂等链。

### 3.3 钱包体系

| 当前能力 | 复用判断 | 扩展要求 |
|---|---|---|
| 用户 Token 钱包 | 直接复用 | Token 发放和退款回收继续走独立权益账本 |
| `xz_commission_wallet_accounts` | 建议作为佣金资金权威账户 | 支持推荐奖励和绩效奖励业务类型 |
| `xz_commission_wallet_ledger` | 直接复用 | `business_type` 增加 ORDER_COMMISSION、REFERRAL_REWARD、PERFORMANCE_REWARD、REFUND_REVERSAL |
| 代理钱包和营销钱包 | 兼容投影 | 不允许继续作为独立写入源 |
| expected/frozen/available/settling/settled/recoverable | 直接复用 | 推荐奖励按配置进入冻结或可提现状态 |

推荐奖励独立建模不等于新增一套钱包。奖励业务事实保存于推荐奖励表，实际余额变化写入现有佣金钱包账本。

### 3.4 提现体系

| 当前能力 | 复用判断 | 扩展要求 |
|---|---|---|
| 结算申请和申请明细 | 直接复用 | 可纳入到期的订单佣金和推荐奖励 |
| 付款批次、付款明细和对账 | 直接复用 | 展示资金来源业务类型和奖励记录编号 |
| 冻结、结算中和已结算状态 | 直接复用 | 退款时阻断未付款批次或生成已付款追偿 |
| 幂等和财务审计 | 直接复用 | 推荐奖励入账、撤销和人工调整必须审计 |

不得为运营中心推荐奖励另建提现系统。代理和运营中心仍通过现有结算申请与付款批次完成提现。

### 3.5 权限后台体系

| 当前能力 | 复用判断 | 扩展要求 |
|---|---|---|
| 企业租户、角色和 RBAC | 直接复用 | 所有渠道数据强制 tenant scope |
| `finance:commission-rule:view/manage` | 扩展复用 | 拆分规则草稿编辑和正式发布权限 |
| 财务审计日志 | 直接复用 | 记录规则发布、奖励确认、负向冲正和提现审核 |
| 客户归属和渠道增长页面 | 扩展复用 | 增加关系历史、推荐链路和异常处理 |
| 企业管理页面 | 扩展复用 | 增加运营中心政策、目标和奖励状态 |

建议新增权限：

| 权限代码 | 用途 |
|---|---|
| `channel:rule-set:view` | 查看规则集和历史版本 |
| `channel:rule-set:edit` | 编辑草稿规则 |
| `channel:rule-set:publish` | 校验并发布规则版本 |
| `channel:simulator:execute` | 执行商业规则模拟 |
| `channel:relation:view` | 查看渠道关系和历史 |
| `channel:relation:adjust` | 调整渠道关系 |
| `channel:referral-reward:view` | 查看推荐奖励 |
| `channel:referral-reward:manage` | 配置推荐奖励规则 |
| `channel:referral-reward:reverse` | 人工冲正推荐奖励 |
| `channel:operation-center:manage` | 管理运营中心政策和目标 |

## 4. 差异分析

| V1.3.1 要求 | 当前状态 | 匹配结果 | 处理建议 |
|---|---|---|---|
| 代理无限发展 | 父代理字段可表达无限关系 | 部分匹配 | 增加历史、生效期、防环和调整审计 |
| 单笔只算直属代理和运营中心 | 默认规则金额接近目标 | 部分匹配 | 新规则服务禁止递归，旧多级规则退出权威路径 |
| 推荐奖励独立建模 | 当前无独立推荐奖励领域 | 不匹配 | 新增规则、事件、奖励记录和负向记录，复用钱包账本 |
| 运营中心推荐运营中心 3000 元 | 无完整实现 | 不匹配 | 新增 OPERATION_CENTER_REFERS_OPERATION_CENTER 场景 |
| 代理推荐运营中心 1000 + 2000 元 | 无完整实现 | 不匹配 | 奖励代理和该代理所属运营中心，保存归属快照 |
| 所有金额、比例、周期后台配置 | 套餐和权益仍有代码常量 | 不匹配 | 数据库已发布规则作为唯一权威源 |
| 整套规则版本化 | 单条佣金规则已有版本 | 部分匹配 | 增加规则集头表、原子发布和不可变历史版本 |
| 历史订单按历史规则 | 有 rule_id/version 和部分订单快照 | 部分匹配 | 增加完整规则、权益和关系快照 |
| 模拟计算 | 有计算引擎，无模拟入口 | 不匹配 | 新增无副作用模拟 API 和页面 |
| 退款冲减 | 数据表支持负向佣金和钱包变动 | 部分匹配 | 增加统一退款/奖励撤销编排 |
| 钱包与提现复用 | 已有完整基础但存在多套投影 | 基本匹配 | 指定权威账本，不新增平行钱包和提现 |

## 5. 数据库设计

### 5.1 继续复用的权威结构

| 结构 | 定位 |
|---|---|
| `xz_users` | 唯一用户主体 |
| `xz_agent_profiles` | 当前代理身份和当前直属关系投影 |
| 运营中心档案 | 当前运营中心身份 |
| `xz_orders` | 订单和支付履约业务凭证 |
| `xz_commission_rules` | 订单现金分润规则明细 |
| `xz_commission_records` | 不可变正向/负向订单佣金事实 |
| `xz_commission_wallet_accounts` | 代理、运营中心佣金账户 |
| `xz_commission_wallet_ledger` | 佣金、推荐奖励和绩效奖励资金账本 |
| 结算申请与付款批次 | 提现和付款权威状态机 |
| 财务审计日志 | 高风险财务操作审计 |

### 5.2 建议新增或扩展的结构

#### `xz_commercial_rule_sets`

作为整套商业规则版本头表：

| 字段 | 说明 |
|---|---|
| `id`、`tenant_id` | 规则集身份和租户边界 |
| `rule_set_code`、`version` | 业务规则集编码和版本 |
| `status` | DRAFT、PUBLISHED、RETIRED、ARCHIVED |
| `effective_start_at`、`effective_end_at` | 生效窗口 |
| `published_at`、`published_by` | 发布审计 |
| `config_snapshot` | 套餐、权益、层级、周期和退款政策完整快照 |

扩展 `xz_commission_rules.rule_set_id`，将会员订单、代理订单和平台剩余规则关联到同一规则集版本。已发布规则集和规则项均禁止原地修改。

#### `xz_channel_relation_history`

保存会员、代理和运营中心关系的有效期历史：

| 字段 | 说明 |
|---|---|
| `subject_type`、`subject_id` | MEMBER 或 AGENT |
| `direct_agent_id` | 当时直属代理 |
| `operation_center_id` | 当时所属运营中心 |
| `effective_start_at`、`effective_end_at` | 关系生效区间 |
| `source_type`、`source_id` | 邀请码、后台调整、迁移等来源 |
| `change_reason`、`approved_by` | 调整原因和审批人 |

#### `xz_order_commercial_snapshots`

保存订单下单/履约时的不可变商业快照：

| 字段组 | 内容 |
|---|---|
| 规则 | 规则集 ID、版本、规则明细快照 |
| 套餐 | 标价、实付、Token 权益、有效期 |
| 关系 | 购买用户、直属代理、所属运营中心和关系来源 |
| 计算 | 各受益方金额、平台结算、舍入和校验结果 |
| 审计 | 幂等键、request id、引擎版本和创建时间 |

#### `xz_referral_reward_rules`

推荐奖励独立规则表：

| 字段 | 说明 |
|---|---|
| `rule_set_id`、`version` | 所属商业规则集和版本 |
| `scenario_code` | OC_REFERS_OC 或 AGENT_REFERS_OC |
| `trigger_event` | 默认 OPERATION_CENTER_ACTIVATED |
| `beneficiary_selector` | REFERRER 或 REFERRER_OPERATION_CENTER |
| `beneficiary_role` | AGENT 或 OPERATION_CENTER |
| `calculation_type` | FIXED_AMOUNT 或可扩展比例类型 |
| `amount_cents`、`percentage_bps` | 配置金额或比例 |
| `freeze_days`、`reversal_policy` | 冻结和撤销策略 |
| `effective_start_at`、`effective_end_at` | 生效窗口 |

#### `xz_referral_events`

保存推荐关系和触发事实：

| 字段 | 说明 |
|---|---|
| `referred_operation_center_id` | 被推荐运营中心 |
| `referrer_type`、`referrer_id` | 推荐运营中心或推荐代理 |
| `referrer_operation_center_id` | 推荐代理当时所属运营中心快照 |
| `source_type`、`source_id` | 推荐码、邀请记录或后台录入 |
| `activation_order_id` | 被推荐运营中心开通订单 |
| `status`、`qualified_at` | 待资格、已满足、已撤销 |
| `idempotency_key` | 防止重复触发 |

#### `xz_referral_reward_records`

保存独立推荐奖励事实：

| 字段 | 说明 |
|---|---|
| `referral_event_id` | 推荐事件 |
| `rule_id`、`rule_version` | 原奖励规则版本 |
| `beneficiary_type`、`beneficiary_id` | 实际受益人 |
| `amount_cents` | 正向或负向金额 |
| `record_type` | REWARD、REVERSAL、ADJUSTMENT |
| `status` | EXPECTED、FROZEN、AVAILABLE、SETTLING、SETTLED、REVERSED |
| `reversal_of_id` | 负向记录对应原记录 |
| `idempotency_key` | 同场景同受益人唯一入账 |
| `rule_snapshot`、`relation_snapshot` | 完整规则和关系快照 |

推荐奖励记录产生后，通过 `xz_commission_wallet_ledger.business_type = REFERRAL_REWARD` 影响现有佣金钱包，不进入 `xz_commission_records` 的订单佣金口径。

#### `xz_commercial_adjustments`

作为订单退款、推荐奖励撤销和绩效奖励撤销的统一编排头表，记录原业务类型、原业务 ID、退款/撤销金额、原规则版本、状态、幂等键和失败恢复信息。资金事实继续写入对应负向记录和钱包账本。

### 5.3 运营中心政策结构

建议新增：

| 表 | 用途 |
|---|---|
| `xz_operation_center_policies` | 技术服务费、目标周期、目标指标、奖励金额和版本 |
| `xz_operation_center_goal_periods` | 每个运营中心每个周期的目标和完成值 |
| `xz_operation_center_performance_rewards` | 达标奖励、规则快照、状态和负向冲正 |

推荐奖励与绩效奖励分别建模，但均可复用现有佣金钱包和提现体系。

## 6. API 设计

### 6.1 复用与收敛现有 API

| 现有 API | 处理方式 |
|---|---|
| `/api/v1/admin/commission-rules` | 纳入规则集草稿和版本查询，已发布规则禁止原地更新 |
| `/api/v1/admin/marketing/commission-rules` | 标记为兼容接口，不再承载 V1.3.1 新业务规则 |
| 订单、支付、微信虚拟支付 API | 保持现有入口，履约时调用统一商业规则服务 |
| 钱包、结算申请、付款批次 API | 扩展业务来源展示，不新增平行接口族 |
| 客户归属和企业管理 API | 扩展渠道历史、推荐关系和运营中心政策 |

### 6.2 规则和模拟 API

| API | 用途 |
|---|---|
| `GET /api/v1/admin/channel-rule-sets` | 查询规则集和历史版本 |
| `POST /api/v1/admin/channel-rule-sets` | 创建草稿 |
| `POST /api/v1/admin/channel-rule-sets/:id/clone` | 从历史版本复制新草稿 |
| `POST /api/v1/admin/channel-rule-sets/:id/validate` | 金额守恒、窗口冲突和完整性校验 |
| `POST /api/v1/admin/channel-rule-sets/:id/publish` | 原子发布规则集 |
| `GET /api/v1/admin/channel-rule-sets/:id/diff` | 比较规则版本差异 |
| `POST /api/v1/admin/channel-rule-simulator/calculate` | 模拟订单分润或推荐奖励 |
| `POST /api/v1/admin/channel-rule-simulator/replay-order` | 按历史订单快照重放 |

模拟响应至少包含：规则版本、场景、关系解析、Token 权益、订单收益、推荐奖励、平台结算、舍入明细、守恒校验和解释文本。模拟请求不得创建订单、支付、奖励、钱包或提现记录。

### 6.3 推荐奖励 API

| API | 用途 |
|---|---|
| `GET /api/v1/admin/referral-reward-rules` | 查询推荐奖励规则及版本 |
| `GET /api/v1/admin/referral-events` | 查询推荐关系、资格和触发状态 |
| `GET /api/v1/admin/referral-reward-records` | 查询奖励、冻结、可提现和冲正记录 |
| `GET /api/v1/admin/referral-reward-records/:id` | 查看规则与关系快照 |
| `POST /api/v1/admin/referral-events/:id/re-evaluate` | 幂等重新评估资格，不重复发奖 |
| `POST /api/v1/admin/referral-reward-records/:id/reverse` | 有权限地执行人工冲正 |
| `GET /api/v1/admin/operation-center-goals` | 查询运营中心目标周期 |
| `POST /api/v1/admin/operation-center-rewards/:id/grant` | 发放运营绩效奖励 |

推荐事件自动触发应由内部领域事件完成，管理 API 不允许直接传入奖励金额或受益人覆盖已发布规则。

## 7. 后台页面设计

| 页面 | 核心功能 |
|---|---|
| 渠道生态中心 | 运营中心、代理、会员、订单、分润、奖励、退款和待办总览 |
| 商业规则中心 | 规则集草稿、版本、差异、校验、发布、停用和审计 |
| 套餐中心 | 价格、Token 权益、周期和关联规则版本 |
| 渠道关系管理 | 无限关系树、直属代理、运营中心归属、历史和异常 |
| 分润中心 | 订单商业快照、订单佣金、冻结、结算和负向冲正 |
| 推荐奖励中心 | 推荐事件、资格、受益人快照、3000/1000/2000 奖励和撤销 |
| 运营中心管理 | 开通、技术服务费、年度目标、绩效奖励和状态 |
| 钱包中心 | Token、佣金、冻结、可提现、已提现、追偿和完整流水 |
| 提现中心 | 申请、审核、付款批次、来源明细和对账 |
| 商业规则模拟器 | 订单场景、推荐场景、版本对比和历史重放 |
| 数据看板 | GMV、Token 成本、订单佣金、推荐奖励、绩效奖励、平台留存和退款 |

推荐奖励中心应把“推荐奖励”和“订单分润”使用不同标签、筛选和统计口径，避免财务报表混淆。

## 8. 实施计划与阶段验收

### 阶段 0：规则冻结

可复用：V1.3.1 场景、当前默认套餐和金额。  
需扩展：触发资格、退款撤销、冻结周期、预算来源和关系快照时点。  
需新增：推荐奖励场景配置字典和业务审批记录。

验收项：

- 确认单笔订单只计算直属代理和所属运营中心。
- 确认运营中心推荐运营中心默认奖励 3000 元。
- 确认代理推荐运营中心默认奖励代理 1000 元、该代理所属运营中心 2000 元。
- 确认推荐奖励不从 996/5000 订单平台结算中直接拆分，而作为独立营销费用入账。
- 确认推荐奖励触发事件、资格条件、冻结期和退款撤销政策。
- 未确认前不得进入阶段 1。

### 阶段 1：数据库与规则治理

可复用：现有用户、订单、代理档案、佣金规则、钱包和提现表。  
需扩展：规则集外键、已发布不可变约束、权威钱包标识和业务类型。  
需新增：规则集、关系历史、订单商业快照、推荐规则、推荐事件、推荐奖励记录和统一调整记录。

验收项：

- 迁移只增量扩展，不删除现有业务数据。
- 新表全部包含 tenant scope、幂等键、状态、审计时间和必要唯一约束。
- 同一被推荐运营中心不会重复生成同一奖励。
- 已发布规则和历史奖励快照不可原地修改。
- 旧规则和旧钱包有明确的只读兼容及迁移路径。

### 阶段 2：统一规则服务与模拟器

可复用：CommissionEngine。  
需扩展：规则集解析、关系解析、推荐奖励解释和版本重放。  
需新增：规则发布、版本差异和无副作用模拟 API。

验收项：

- 会员订单模拟：99600 - 40000 - 30000 - 20000 = 9600 分。
- 代理订单模拟：99600 - 20000 - 30000 - 20000 = 29600 分。
- 运营中心推荐运营中心模拟：推荐运营中心奖励 300000 分。
- 代理推荐运营中心模拟：代理奖励 100000 分，代理所属运营中心奖励 200000 分。
- 任何模拟都不产生订单、奖励或钱包流水。
- 发布新规则后，旧版本模拟和历史重放结果保持不变。

### 阶段 3：订单支付与统一商业履约

可复用：订单、支付状态机、支付回调、微信虚拟支付和权益发放。  
需扩展：选择规则集、写商业快照、调用统一分润服务。  
需新增：旧固定结算与旧营销规则的迁移开关和对账任务。

验收项：

- 重复支付回调只生成一次权益和佣金。
- 新订单不递归查询上级代理。
- 套餐金额和 Token 权益只由服务端已发布规则决定。
- 订单、权益、佣金和平台结算保持事务一致或可恢复。

### 阶段 4：推荐奖励、运营中心政策和退款冲正

可复用：运营中心激活、佣金钱包、钱包账本、结算和付款批次。  
需扩展：领域事件、奖励资格、冻结和负向冲正。  
需新增：推荐奖励服务、运营绩效服务和统一调整编排。

验收项：

- 运营中心 A 推荐运营中心 B，B 有效激活后 A 仅获得一次 3000 元奖励。
- 代理 A 推荐运营中心 B，A 获得 1000 元，A 当时所属运营中心获得 2000 元。
- A 的上级代理不参与任何推荐奖励。
- A 后续更换运营中心不改变历史奖励受益人。
- B 的开通订单退款时按原规则版本生成负向奖励和钱包流水。
- 奖励已进入提现中或已结算时，系统能阻断、冲正或生成追偿记录。

### 阶段 5：管理后台与数据看板

可复用：Vue 3、Pinia、Axios、Element Plus、现有 API Client、权限和管理页面壳。  
需扩展：客户归属、渠道增长、订单、钱包和财务页面。  
需新增：规则中心、推荐奖励中心、模拟器、运营中心政策和渠道看板。

验收项：

- 页面不得硬编码金额、比例、层级或周期。
- 规则发布前必须经过校验和模拟。
- 推荐奖励和订单分润分口径展示，汇总可对账。
- 关系调整、奖励冲正、规则发布和提现审核均有独立权限和审计。

每阶段完成后单独提交验收结果，未经业务确认不得自动进入下一阶段。

## 9. 主要风险

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 推荐奖励被错误并入订单分润 | P0 | 独立规则、事件和奖励记录，钱包只复用资金账本 |
| 推荐奖励触发时点不明确 | P0 | 阶段 0 冻结支付、履约、认证和激活条件 |
| 三套分润路径结果不一致 | P0 | 新订单收敛到统一规则集，旧入口只读兼容 |
| 重复回调导致重复奖励 | P0 | 支付、激活、推荐事件和奖励记录形成统一幂等链 |
| 关系调整改变历史受益人 | P0 | 推荐事件和订单都保存关系快照 |
| 退款发生时奖励已经提现 | P0 | 冻结期、批次锁、recoverable 和追偿任务 |
| 规则发布后历史结果变化 | P0 | 整套规则原子版本、已发布不可变和业务快照 |
| 多钱包并行写入导致余额不一致 | P0 | 佣金钱包账本作为唯一资金写入源，旧钱包只读投影 |
| 金额仍被代码默认值覆盖 | P1 | 数据库已发布规则作为唯一运行权威源 |
| 跨租户读取奖励或钱包 | P1 | 全表 tenant scope、联合约束、RBAC 和越权测试 |

## 10. 待确认项

进入开发前需要业务方确认：

1. 推荐奖励是否独立列为平台营销费用，不冲减 996 元或 5000 元订单的平台结算。
2. 推荐奖励默认在被推荐运营中心完成支付并正式激活后触发，还是需要额外认证/考核条件。
3. 推荐奖励的冻结周期、可提现时间和退款撤销期限。
4. 代理推荐运营中心时，2000 元奖励归属“推荐事件发生时”还是“被推荐运营中心激活时”的代理所属运营中心。建议使用激活时快照。
5. 被推荐运营中心部分退款、全额退款、身份取消时的奖励撤销比例。
6. 运营中心年度绩效奖励与推荐奖励是否可以同时获得，以及各自预算和财务科目。

上述六项确认后，才具备进入阶段 1 数据库迁移详细设计的条件。
